# Spec — IndexNow submission

- **Date:** 2026-07-30
- **Status:** approved
- **Owner:** storefront + deploy

## Goal

Notify Bing, Yandex and the other IndexNow participants the moment published
content changes, instead of waiting for a crawl. `AGENTS.md` ("Sitemaps and
discovery") already requires this; the site currently has sitemaps but no ping.

Two moving parts are needed:

1. **A key file** at the site root — `https://peptideeinkaufen.de/<key>.txt`
   containing exactly the key. This is how the protocol proves the submitter
   controls the host. It is public by design, not a secret.
2. **A submitter** that POSTs the changed URLs to `api.indexnow.org` after a
   deploy has published them.

## The two constraints that shape the design

**The storefront is static and published by `deploy.sh`.** Nothing changes on the
site between deploys, so the submission belongs at the end of a deploy — *after*
`rsync` puts the new files in the web root. Submitting during the Astro build
would tell crawlers to fetch URLs that still serve the previous release.

**The site is public, with the launch blockers still open.** The pre-launch gate
came off on 2026-07-29 by explicit decision (`deploy.md`, "What is still open"),
so the storefront is crawlable while purity values are fabricated and the legal
pages render `[Platzhalter]`. Bing will index it regardless of IndexNow; the only
thing IndexNow changes is the speed. So **enabling it in production is a decision
for a human**, and the design makes that decision a single one: `INDEXNOW_KEY`
unset in `/srv/peptides/.env` means no key file and no submission, and it stays
unset in this change.

The submitter still **verifies the key file is publicly readable before
submitting**. That is worth having independently of the gate: it catches a key
rotated in `.env` but not deployed, and if the site is ever re-gated the feature
degrades to a clean skip instead of hammering a rejection. Exempting the key file
from a restored gate would be pointless — a site-wide `X-Robots-Tag: noindex`
blocks indexing anyway, so there would be nothing to gain by inviting a crawl.

## Scope

### Key file — `storefront/src/pages/[indexnowKey].txt.ts`

A dynamic route whose single param *is* the key, so the emitted file is
`/<key>.txt`. Driven by `INDEXNOW_KEY`:

- Unset → `getStaticPaths` returns `[]`, no file is emitted. Same off-switch
  convention as `PUBLIC_GA_MEASUREMENT_ID`.
- Set but not matching the protocol's charset (8–128 chars of `a-zA-Z0-9-`) →
  no file, and a build-time warning. A malformed key would otherwise produce a
  garbage URL that fails validation later, at a point much harder to diagnose.

Not `PUBLIC_`-prefixed: the key is public in the sense that it is served at a
URL, but no browser code needs it, and shipping it into the client bundle would
be pointless. Astro exposes non-prefixed variables to build-time code only, which
is exactly the required reach.

The route file lives beside the static `robots.txt.ts` / `llms.txt.ts` routes;
Astro gives static routes priority over dynamic ones, so `[indexnowKey].txt`
cannot shadow them.

### Submitter — `storefront/scripts/indexnow-submit.mjs`

Plain Node (>= 22.12, so `fetch` is global), no dependencies, no Astro imports —
it runs against the *built output*, after publish.

- **URL source: `dist/sitemap-*.xml`.** The sitemaps are already generated from
  `content-index.ts`, the single inventory of what the site publishes. Reading
  them back means the submitter cannot drift from what shipped, and draft
  filtering stays in one place. The index file `sitemap.xml` has no dash and is
  skipped.
- **Change detection: a SHA-256 of each URL's built HTML**, compared against a
  state file from the previous run. Not `lastmod`: the pages and category
  sitemaps carry build time there, so every deploy would look like a change to
  every page, and IndexNow explicitly asks for changed URLs only. Hashing the
  actual bytes answers the real question. (Verified: nothing time-varying is
  emitted into the HTML, so an unchanged page hashes identically across builds.)
- **Preflight, all of which skip cleanly with exit 0** — a deploy must not fail
  because a search engine is unreachable:
  - no `INDEXNOW_KEY`
  - origin is not `https:` (a localhost build has nothing to submit)
  - `GET <origin>/<key>.txt` is not 200 with the key as its body — catches a key
    that was rotated in `.env` but not yet deployed, and a re-gated site
  - no changed URLs
- **Submission:** one `POST https://api.indexnow.org/indexnow` per batch of
  10,000 URLs with `{ host, key, keyLocation, urlList }`. The shared endpoint
  forwards to every participating engine, so Bing and Yandex do not need
  separate calls. `200`/`202` are both success (`202` means key validation is
  still pending).
- **Flags:** `--dry-run` (print, submit nothing, leave state untouched),
  `--all` (ignore state — a full resubmission, which is what launch day wants),
  `--state <path>`, `--dist <path>`.
- State file defaults to `storefront/.indexnow-state.json`, git-ignored;
  `deploy.sh` points it at `/srv/peptides/indexnow-state.json` so it survives
  release pruning.

### Deploy wiring — `deploy/deploy.sh`

- `INDEXNOW_KEY` written into the build `.env` alongside the other variables, so
  the key file is emitted by the same build that produces the pages.
- A new step after the storefront is published, run as the deploy user against
  the live origin, non-fatal: a failed ping warns and the deploy still succeeds.

### Docs

- `docs/indexnow.md` — the runbook: where the key comes from, how to verify, why
  it is off in production, how to trigger a manual submission, troubleshooting by
  HTTP status.
- `AGENTS.md` gains a pointer to it from the existing IndexNow bullet;
  `README.md` and `deploy/.env.template` document `INDEXNOW_KEY`;
  `go-live-checklist.md` and `deploy.md` get the activation step.

## Non-goals

- **Turning it on in production.** The code ships with `INDEXNOW_KEY` unset on the
  server. Enabling it is a decision for a human, per `go-live-checklist.md`.
- **Touching the gate**, in either direction — neither restoring it nor exempting
  the key file from a restored one.
- **Submitting on Medusa product edits.** Tempting, but the storefront is static:
  an edited product is not visible until a rebuild, so pinging on the admin event
  would advertise a URL whose content has not changed yet. The deploy is the
  correct trigger and remains the only one.
- **A Bing Webmaster Tools API integration** (URL submission quota, crawl stats).
  IndexNow needs no account or token; adding one would add a real secret to
  manage for no gain here.
- **Google.** Google does not consume IndexNow. Its discovery path stays
  Search Console plus the sitemaps.

## Verification

```bash
cd storefront
npm run typecheck
npm run build                      # backend must be on :9000
ls dist/*.txt                      # <key>.txt present, contains the key
npm run indexnow -- --dry-run      # skips: origin is http://localhost:4321
```

With `PUBLIC_SITE_URL=https://peptideeinkaufen.de` in a scratch build, the same
command must skip rather than submit — production returns 404 for the key file,
which is not deployed. That is the acceptance criterion for this change: **the
pipeline is wired end to end and provably declines to submit until someone sets
the variable on the server.**

The diff logic is verified against a fixture (`--dist`), which is the only way to
exercise it without a live submission: no state → everything new; unchanged build
→ "nothing changed"; one edited file → exactly one URL; `--all` → everything;
a page deleted from both the sitemap and `dist` → submitted as removed; an
off-host URL and a nested `<image:loc>` → ignored.

Nothing in Bing Webmaster Tools → IndexNow should show submissions, and no deploy
log should show an attempt, until `INDEXNOW_KEY` is set on the server.
